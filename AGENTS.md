# AGENTS.md | Правила для Codex в Task-Ayuza

## Источники требований
1. Каноническое ТЗ 2.2 (предполагаемый путь `docs/TZ-2.2.md`); если файла нет, сообщить об отсутствии и не выдумывать требования.
2. `PROJECT.md`: только текущий этап, статус и передача контекста.
3. Этот файл: правила работы с репозиторием.
При конфликте требований не менять бизнес-логику самостоятельно.

## Режим работы: минимум токенов
- Один запрос/чат = один небольшой законченный объём работ, одна понятная цель и критерии приёмки.
- В начале прочитать этот файл, краткий статус из `PROJECT.md`, релевантные модули кода и только нужные разделы ТЗ. Не сканировать всё подряд и не пересказывать документацию.
- Перед изменениями кратко указать цель, границы и проверки; после — кратко показать результат.
- Вносить минимально необходимые изменения; избегать переписывания файлов целиком, лишних зависимостей, массового рефакторинга и генерации объёмных отчётов.
- Запускать сначала точечные тесты; полный прогон обязателен на интеграционных контрольных точках. Не запускать бесконечные циклы исправлений.
- Следующую задачу не начинать без новой команды; сложные задачи дробить на небольшие этапы.

## Неизменяемые ограничения
- Только бесплатные технологии и open source. Никаких платных API, лицензий, внешней платной AI-обработки и подписок.
- Веб/PWA, один корпоративный контур, PostgreSQL, размещение сервера и рабочих данных в РФ. GitHub — код/документация/CI, никогда не секреты, `.env`, реальные ПДн, дампы БД, аудио или рабочие записи.
- Без Sol Flow. Не проводить деплой, миграции боевой БД или изменения production без отдельного разрешения.
- Безопасность не отключать ради скорости: серверная проверка прав, HTTPS, аудит, защита доступа, резервные копии и проверяемое восстановление, требования 152-ФЗ.
- Задача может не иметь проекта; команда-исполнитель, персональный исполнитель и владелец результата — разные поля/роли. Допускаются задачи команд без персонального исполнителя.
- Зависимости и блокеры не смешивать с реестром рисков. Учитывать историю закрытия и переоткрытия. Голосовое создание — локальное распознавание + пользовательская правка + явное подтверждение сохранения.
- UI: минималистичный, адаптивный, ПК/Android/iPhone; список, Kanban, Gantt, календарь, аналитика, центр рисков; в шапке фактические версия и время релиза.

## Проверка и результат
- Каждое изменение: короткие критерии приёмки, тесты позитивных/негативных случаев, проверка прав доступа и регрессий затронутой логики.
- Не утверждать, что тесты, аудит, деплой или проверка интерфейса выполнены, если не были выполнены.
- Обновить в `PROJECT.md` фактический статус, изменённые компоненты, проведённые тесты, блокеры, следующую задачу. Не накапливать хронику чатов: достаточно текущего состояния и ссылки на commit/PR, если они есть.
- Финальный ответ всегда: **сделано / проверено / осталось / статус PROJECT.md / задача следующей сессии / готовый промпт / новый чат + рекомендуемый режим и модель**.
- Выбор: **Codex** для реализации/тестов (модель из доступных); **GPT-6 Medium** для обычного ревью/ТЗ; **GPT-6 High** для архитектуры, БД и безопасности; **GPT-6 Instant** для простых действий. Выбор обосновать одной фразой.
