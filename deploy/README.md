# Запуск Task-Ayuza на своём компьютере с публичной ссылкой

Временная схема по решению владельца (Issue #162): сервер — ноутбук владельца на Windows, доступ по ссылке `https://task-ayuza.<ваша-сеть>.ts.net` с любого устройства, в обычном браузере, без установки программ. Всё бесплатно.

- Данные (PostgreSQL) хранятся только на этом компьютере.
- HTTPS завершается на этом компьютере (контейнер Tailscale). Tailscale пересылает только зашифрованный трафик.
- На компьютере не открывается ни одного порта: в интернет смотрит только Tailscale Funnel.
- Ссылка работает, пока компьютер включён, не спит и подключён к интернету.

## Один раз: подготовка

1. **Docker Desktop** для Windows: https://www.docker.com/products/docker-desktop/ (бесплатен для небольших компаний). В настройках включите *Start Docker Desktop when you sign in*.
2. **Git для Windows**, если его нет: https://git-scm.com/download/win
3. **Учётная запись Tailscale** (бесплатный тариф): https://login.tailscale.com. Приложение Tailscale на этот компьютер ставить не нужно: Tailscale работает внутри Docker.
4. В панели Tailscale (https://login.tailscale.com/admin):
   - **DNS** → включите *MagicDNS* и *HTTPS Certificates*. Там же видно имя вашей сети (`xxxx.ts.net`), из него получится ссылка.
   - **Access controls** → в политике должен быть разрешён Funnel. Если его нет, добавьте:
     ```json
     "nodeAttrs": [{"target": ["autogroup:member"], "attr": ["funnel"]}]
     ```
   - **Settings → Keys → Generate auth key**: не *Reusable*, не *Ephemeral*. Скопируйте ключ `tskey-auth-…`, он понадобится один раз.
5. **Электропитание Windows**: *Параметры → Система → Питание* → при питании от сети «Переводить в спящий режим» — *Никогда*.

## Запуск

В PowerShell:

```powershell
git clone https://github.com/Ivankorytnik/Task-Ayuza.git
cd Task-Ayuza
powershell -ExecutionPolicy Bypass -File deploy\setup.ps1
```

При первом запуске скрипт попросит auth key Tailscale. Он сам сгенерирует все пароли и ключи в `deploy\.env`: этот файл доступен только вашей учётной записи и в Git не попадает. Затем скрипт поднимет базу, миграции, Tailscale и приложение и напечатает ссылку.

**Не теряйте `deploy\.env`.** В нём ключи, без которых не расшифровать MFA и не войти в базу. Храните копию в менеджере паролей.

## Повседневное

| Что | Команда (из папки `Task-Ayuza`) |
|---|---|
| Остановить (данные сохраняются) | `docker compose -f deploy\docker-compose.yml --env-file deploy\.env stop` |

| Журналы | `docker compose -f deploy\docker-compose.yml --env-file deploy\.env logs --tail 100 backend tailscale` |

## После перезагрузки Windows

**Без входа в Windows запуск невозможен.** Docker Desktop — обычная программа пользователя: она стартует только после входа в учётную запись, службы «до входа» у неё нет. Поэтому схема такая: Windows входит сама, сразу блокирует экран, а приложение поднимается в фоне.

Что уже сделано скриптом `setup.ps1`: задача Планировщика *Task-Ayuza start* при каждом входе ждёт Docker Desktop (до 10 минут), поднимает контейнеры, проверяет ссылку и пишет итог в `deploy\backups\start.log` (`OK` или `FAIL`). Если включён автовход, она же сразу блокирует экран.

Что нужно сделать один раз вручную, чтобы Windows входила сама:

1. *Параметры → Учётные записи → Варианты входа* → выключите «Для повышения безопасности разрешить вход Windows Hello только для учётных записей Майкрософт». Иначе автовход не сработает.
2. Скачайте **Autologon** от Microsoft: https://learn.microsoft.com/sysinternals/downloads/autologon и запустите `Autologon64.exe`.
3. Введите имя пользователя, домен (имя компьютера) и пароль Windows, нажмите **Enable**. Пароль хранится в Windows в зашифрованном виде, в проект не попадает.
4. Перезагрузите компьютер, ничего не нажимая. Через 2–5 минут проверьте ссылку с телефона и строку `OK` в `deploy\backups\start.log`.

Риск: тот, кто сам включит ноутбук, на несколько секунд увидит рабочий стол до блокировки. Держите ноутбук у себя, как и раньше. Выключить автовход: снова Autologon → **Disable**.

Если ссылка не отвечает, запустите `setup.ps1` ещё раз.

Переименуем при переезде на сервер в РФ, когда база всё равно создаётся заново из резервной копии.

## Резервные копии

`setup.ps1` настраивает их сам:

- **Ключ шифрования (`age`)** создаётся один раз. Открытая часть шифрует каждую копию, закрытая лежит в `deploy\backup-keys\backup-identity.txt` и нужна только для восстановления. **Сохраните этот файл и `deploy\.env` в менеджере паролей и на рабочем компьютере.** Без них копию не открыть.
- **Ежедневно в 13:00** (или сразу, как компьютер включится) задача Планировщика *Task-Ayuza backup* делает зашифрованную копию в `deploy\backups`. Копии хранятся 30 дней.
- **Вторая копия.** Если при установке указано имя рабочего компьютера в Tailscale, копия уходит на него через Taildrop. На рабочем компьютере должно стоять приложение Tailscale, вход под той же учётной записью. Файл придёт в «Загрузки» или по уведомлению Tailscale. Если имя не указано, в журнале будет `SKIP copy`; чтобы добавить его позже, снова запустите `setup.ps1`: пока значение пустое, он спрашивает ещё раз. Если рабочий компьютер выключен или не в той же сети Tailscale, в журнале будет `FAIL copy: ... not a Taildrop target`.
- **По понедельникам** выполняется проверка восстановления: новейшая копия расшифровывается и разворачивается в одноразовую базу внутри контейнера, затем схема и набор таблиц сравниваются с рабочей базой. Рабочая база не меняется.
- **Журнал:** `deploy\backups\backup.log`. Строка `FAIL` означает, что копия или проверка не удались.
- **Вручную:** `powershell -ExecutionPolicy Bypass -File deploy\backup.ps1 -RestoreCheck`.

**В Git резервные копии не кладутся никогда**: репозиторий публичный, а правила проекта запрещают дампы и персональные данные. Папки `deploy\backups` и `deploy\backup-keys` исключены через `.gitignore`.

**Восстановление на новом компьютере** — отдельная задача, она ещё не автоматизирована. Понадобятся: старый `deploy\.env` (в нём ключи MFA и паролей), `backup-identity.txt` и последняя копия `.dump.age`. Порядок тот же, что в `deploy/backup/restore-check.sh`: роли и пустая схема, `pg_restore` от имени роли migrator, затем гранты.

## Первичная настройка: организация, люди, пространство

Регистрации через сайт нет намеренно, а административных экранов пока нет. Всё делается командой `deploy\admin.ps1` на этом компьютере. Пароли и коды MFA вводятся по запросу, в командной строке их нет.

Правила доступа запрещают выдавать права самому себе: для setup нужны два разных участника, роль себе не выдаётся, себя администратором не назначают. **Пока вы работаете один**, нужны три учётные записи:

| Учётная запись | Для чего | MFA |
|---|---|---|
| `ivan` | ежедневная работа на сайте | не обязательно |
| `ivan-owner` | владелец системы, только для настройки | да |
| `ivan-admin` | второй утверждающий, системный администратор и администратор пространства | да |

Пока вы один, правило двух людей выполняется только формально: всё держится на ваших паролях и MFA. Используйте разные пароли и храните их в менеджере паролей. Для MFA подойдёт одно приложение с двумя записями.

Каждый вход тратит одну из 5 попыток на логин за 15 минут, и успешные тоже. Поэтому свои команды выполняйте одной сессией (`session`).

### Быстрый путь: одна команда

```powershell
powershell -ExecutionPolicy Bypass -File deploy\admin.ps1 quickstart "Название компании"
```

В Windows запуск `.ps1` по умолчанию запрещён («выполнение сценариев отключено»), поэтому здесь и ниже `deploy\admin.ps1 …` запускайте так: `powershell -ExecutionPolicy Bypass -File deploy\admin.ps1 …`.

Команда выполняет шаги 1–9 ниже по порядку и через те же проверки: настоящие входы, CSRF, свежий код MFA, аудит. Правила доступа и двух участников не обходятся, меньше только набирать вручную. По ходу она попросит:

- **постоянный пароль** для `ivan`, `ivan-owner` и `ivan-admin`, каждый дважды (15–128 символов, у каждой записи свой). Временные пароли используются внутри команды и не показываются, заходить на сайт для смены пароля не нужно;
- **подключить MFA** для `ivan-owner` и `ivan-admin`: команда покажет ключ (Яндекс Ключ или Google Authenticator → «Ввести ключ вручную») и резервные коды, затем попросит код из приложения. **Резервные коды сохраните**;
- **код MFA** ещё раз, если между шагами прошло больше 14 минут.

В конце печатается `status`, затем работайте на сайте под `ivan`. Если команду прервали, запустите её снова: сделанное пропускается, пароли уже заданных записей не меняются. Учётная запись, оставшаяся с временным паролем, получает новый временный пароль, и команда снова просит постоянный.

Параметры (по умолчанию): `--login ivan` (служебные записи получат `-owner` и `-admin`), `--name "Иван"` (отображаемое имя, без параметра — логин), `--workspace "Работа"`, `--team "Команда"`.

### Вручную, по шагам

1. Организация и учётные записи. Временные пароли действуют 24 часа и показываются один раз:
   ```powershell
   deploy\admin.ps1 init-org "Название компании"
   deploy\admin.ps1 create-user ivan "Иван"
   deploy\admin.ps1 create-user ivan-owner "Иван (владелец системы)"
   deploy\admin.ps1 create-user ivan-admin "Иван (администратор)"
   ```
2. По ссылке войдите **в каждую** учётную запись с временным паролем и задайте постоянный (15–128 символов, у каждой свой). Выходите и входите в следующую.
3. Подключите MFA для двух служебных записей: приложение Яндекс Ключ или Google Authenticator → «Ввести ключ вручную». **Резервные коды сохраните.**
   ```powershell
   deploy\admin.ps1 enroll-mfa ivan-owner
   deploy\admin.ps1 enroll-mfa ivan-admin
   ```
4. Одноразовая процедура: `deploy\admin.ps1 setup ivan-owner ivan-admin`
5. Роль системного администратора:
   ```powershell
   deploy\admin.ps1 session ivan-owner
   ivan-owner> grant-role ivan-admin system_admin
   ivan-owner> exit
   ```
6. Пространство, команда и вы в команде:
   ```powershell
   deploy\admin.ps1 session ivan-admin
   ivan-admin> create-workspace "Работа"
   ivan-admin> create-team "Команда"
   ivan-admin> add-team-member "Команда" ivan
   ivan-admin> exit
   ```
7. Первый администратор пространства (только пока его нет):
   ```powershell
   deploy\admin.ps1 session ivan-owner
   ivan-owner> first-workspace-admin "Работа" ivan-admin
   ivan-owner> exit
   ```
8. Вы — участник пространства, команда работает в нём:
   ```powershell
   deploy\admin.ps1 session ivan-admin
   ivan-admin> add-member "Работа" ivan participant
   ivan-admin> link-team "Работа" "Команда"
   ivan-admin> exit
   ```
9. Проверка: `deploy\admin.ps1 status`. Дальше работайте на сайте под `ivan`.

**Когда появится коллега:** `create-user`, затем `add-member` от `ivan-admin` и `add-team-member` от `ivan-admin`. Он входит по той же ссылке. Позже роль утверждающего можно передать ему, тогда правило двух людей начнёт работать по-настоящему.

**Забыли пароль:** `deploy\admin.ps1 reset-password логин`, все сессии этой учётной записи при этом отзываются.

## Что ещё нужно до работы с реальными данными

1. **Первый запуск и проверка на этом компьютере**: ссылка открывается, первичная настройка пройдена, в журнале бэкапа есть строка `OK restore check`.


## Ограничения временной схемы

- Нет компьютера — нет сервиса: выключение, сон, отсутствие интернета.
- Ссылка только HTTPS: запрос по `http://` Funnel перенаправляет на `https://`, приложение отдаёт `Strict-Transport-Security` (1 год).
- Страница входа доступна из интернета. Защита: лимиты 5 попыток на логин и 100 на адрес за 15 минут, Argon2id, CSRF, `__Host-` cookie, MFA для административных прав.
- Tailscale — зарубежный сервис. Данные он не хранит и содержимого не видит, но знает факт подключений.
- Переезд на сервер в РФ: тот же `deploy/`, данные переносятся из резервной копии.
