## 2. Исполнимые границы M01.1

**Цель:** доказать, что схема управляется отдельно от приложения, runtime не может менять структуру БД, а минимальный аудит защищён от правки.

В репозитории сейчас документация, исходники приложения в дерево не включены. Аудит архива 0.1 сохранён в PROJECT.md. Не распаковывать весь прототип в приложение и не запускать его автоматически. Для M01.1 допустим минимальный каркас на согласованном FastAPI/SQLAlchemy; повторное использование конкретных файлов 0.1 требует их предварительного чтения. Это не разрешение переписать весь прототип.

Будущий набор изменений ограничить:
- минимальными модулями backend: конфигурация, подключение/транзакции, metadata, проверка версии схемы при старте;
- конфигурацией Alembic и **одной начальной ревизией**, без автоматического применения;
- organization: UUID и name, не более одной корпоративной записи; запись создаётся только явной процедурой, не при старте;
- audit_events: UUID, actor_id/session_id/workspace_id пока nullable, entity_kind/entity_id, action, occurred_at, request_id, разрешённые old/new. До появления соответствующих сущностей нет FK на users/sessions/workspaces и гранты. Следующие ревизии добавляют поля/связи после проверки данных. Системная операция явно обозначена, неизвестный человек не подменяется фиктивным пользователем;
- минимальным перечнем фиксированных бесплатных зависимостей, примером конфигурации без секретов, инструкцией ролей и запуска тестов;
- тестами M01.1 и обновлением PROJECT.md.

До будущего изменения назвать конкретные пути файлов. Не добавлять UI, Docker/CI/CD/deploy-конфигурацию или стороннюю инфраструктуру ради каркаса.

**Технические условия:**
1. Явный PostgreSQL DSN, без fallback на SQLite; отсутствие/невалидность конфигурации даёт безопасную ошибку без вывода пароля/DSN.
2. Никакого create_all, DDL, вызова Alembic upgrade или автоматического seed при импорте/старте приложения. Проверка схемы только читает состояние.
3. Одна цепочка Alembic с одним head. Пустая, устаревшая или неизвестная схема блокирует запуск; совместимая версия допускает запуск без изменения данных.
4. Начальная ревизия создаёт только согласованные таблицы/ограничения/индексы. UUID, TIMESTAMPTZ/UTC; никаких projects/tasks, рабочих записей и демонстрационных задач.
5. Минимальный аудит создаётся раньше M02, поскольку без него нельзя принимать M01.2–M01.4. Это технический порядок реализации, не изменение логической модели. Полный task_events и прочая история остаются за границей.
6. Для аудита применяется allowlist полей. Пароли, хеши паролей, токены/их хеши, секреты MFA, резервные коды, DSN, аудио и транскрипты в old/new и логи не попадают. Нет пользовательского CRUD аудита.
7. Версии PostgreSQL/SQLAlchemy/драйвера/Alembic фиксировать в будущей реализации после проверки совместимости/лицензий. Не выдавать выбранные версии за уже проверенные.
8. Существующую рабочую SQLite не искать через получение рабочих данных и не переносить. Обнаружение рабочих данных прекращает этот сценарий до отдельного решения.

### Роли БД

| Роль | Разрешено | Запрещено |
|---|---|---|
| runtime | Подключение, использование прикладной схемы, необходимые DML; audit_events только INSERT и необходимый SELECT | Владение схемой/таблицами, CREATE/ALTER/DROP, изменение alembic_version, UPDATE/DELETE/TRUNCATE аудита, SET ROLE в migrator/backup, superuser/BYPASSRLS |
| migrator | Ручное управление прикладной схемой и ревизиями в разрешённом контуре | Использование приложением; пароль в репозитории; автоматический запуск при старте |
| backup | Чтение объектов, необходимое для выбранного способа копирования | Прикладные записи, DDL, административные права приложения |

Проверять эффективные права, включая PUBLIC, наследование и владение; запрет CREATE относится и к доступным runtime схемам. Создание служебных ролей выполняется отдельно от миграции приложения администратором тестового контура. Runtime не выдаёт себе права. Backup и migrator не являются пользователями трекера. Production backup/restore и RPO/RTO этим этапом не принимаются.

## 3. Приёмка первой сессии M01.1

Все проверки ниже планируются на **реальном изолированном PostgreSQL**, не на SQLite. Тестовые роли/база не имеют доступа к рабочим данным. Перед исполнением необходима новая команда, явно разрешающая код, зависимости и создание/применение миграций только в этом тестовом контуре.

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| A01 | Ручной upgrade пустой тестовой БД до head; повторный upgrade | Ровно одна ожидаемая ревизия; повтор не меняет схему/данные; только organization/audit_events и служебная таблица Alembic |
| A02 | Старт на актуальной схеме под runtime; сравнение структуры и числа записей до/после | Успех без DDL, seed и иных записей |
| A03 | Старт на пустой/устаревшей/неизвестной схеме; неверный или отсутствующий DSN | Отказ с безопасной диагностикой; схема не исправляется автоматически, секреты не раскрываются |
| A04 | Попытки runtime CREATE/ALTER/DROP, изменить alembic_version, переключиться на migrator | Все запрещены эффективными правами |
| A05 | INSERT аудита; затем UPDATE/DELETE/TRUNCATE runtime | Запись разрешена, изменение/удаление запрещены |
| A06 | Тестовая транзакция organization + аудит; принудительная ошибка записи аудита | Полный rollback, без частичного изменения organization |
| A07 | Две транзакции одновременно создают первую organization | Только одна корпоративная запись, второй запрос получает контролируемую ошибку без потери первой |
| A08 | Недопустимые/секретные поля аудита и ошибки подключения | Поля не сохраняются и не выводятся в логах |
| A09 | Роль backup читает разрешённые данные и пытается писать/DDL | Чтение доступно, запись и DDL запрещены |
| A10 | Статическая сверка diff и миграции | Нет DDL на старте, SQLite fallback, несуществующих FK, UI, рабочих данных, секретов и изменений D01–D06 |

Приёмка требует реальных результатов A01–A10 с версией PostgreSQL, командами и кратким итогом; пропущенные проверки отмечаются как «не выполнено», а не «успешно». Если PostgreSQL недоступен, допустим только непроверенный результат для ревью; M01.1 не объявляется принятым. Downgrade/пересоздание допустимы лишь для одноразовой тестовой БД и не являются стратегией восстановления production.

## 4. Первичная настройка и независимое одобрение (M01.4)

Это контракт последующих подэтапов, не дополнительный объём первой сессии.

1. Владелец системы явно определяет свою учётную запись, первого уполномоченного и резервного одобряющего. Не назначать владельца по правилу «первый зарегистрировавшийся» и не создавать публичную регистрацию.
2. Первичное назначение выполняется отдельной однократной закрытой процедурой владельца системы. Она проверяет незавершённость настройки, выполняется транзакционно, оставляет аудит назначения/основания, не открывает рабочие данные и не оставляет универсальный bootstrap-токен или backdoor.
3. До включения административного API обеспечить MFA/TOTP, шифрование секрета ключом вне БД/репозитория, хеширование резервных кодов и аудит. Не включать временный административный обход.
4. Одобряющий является владельцем или назначенным им уполномоченным и **отличается от получателя**. Если владельцу нужен собственный доступ, его одобряет другой уполномоченный. Резервный одобряющий сохраняет возможность независимого решения. Самостоятельное повышение через членства/роль/команду запрещено тем же процессом.
5. Грант содержит пространство, операции, получателя, одобряющего, основание, начало/конец и отзыв. Обычный срок не более 30 дней; аварийный не более 2 часов с независимым одобрением, MFA и полным аудитом. Продление требует нового одобрения, истёкший/отозванный грант не действует.
6. Выдача/отзыв, изменение членства/системной роли и их аудит выполняются атомарно. Повтор не создаёт дополнительных полномочий. Техническое окно идемпотентности до соответствующего API уточняется отдельно; 24 часа не утверждены.
7. Root/DB-superuser остаются эксплуатационной границей. Проект не обещает защитить аудит от владельца БД.

## 5. Проверки M01.2–M01.4 и контрольной точки

| Область | Позитивные | Негативные / конкурентные |
|---|---|---|
| Пользователи/сессии | Вход активного пользователя, смена временного пароля, выход, отзыв всех сессий при сбросе/деактивации | Истёкшая/отозванная сессия, неверный пароль, повтор нормализованного логина включая неактивного, сырой токен в БД, отсутствие CSRF; до смены временного пароля рабочие операции недоступны |
| Защита входа | Одинаковая нормализация при входе и ограничении попыток | Варианты пробелов/регистра, несколько workers и рестарт не обходят ограничение; секреты не попадают в ошибки |
| D01 | Команда явно разрешена в пространстве; уполномоченный активный член получает только делегируемые операции | Само членство в команде не даёт доступа; другая область, неактивное членство, лишняя capability и косвенная самовыдача запрещены |
| D02 | Права вычисляются сервером для конкретного объекта и операции; после появления проектов/задач применяется матрица модели § 4 | Нет глобального admin bypass, доступа к чужой области по UUID/списку/счётчику; чтение не равно export/manage_access. Полная проектно-задачная приёмка только после M02 |
| D03/MFA | Независимо одобренный ограниченный грант и его отзыв | Самоодобрение, неуполномоченный одобряющий, отсутствие MFA, превышение сроков, истёкший/отозванный грант; повторное bootstrap запрещено |
| Атомарность | Изменение доступа и аудит фиксируются вместе | Ошибка аудита откатывает изменение; две правки одной version дают один успех и 409 при сохранённом доступе; после потери доступа конфликт не раскрывает объект |
| Гонки сессий/ACL | Параллельные транзакции синхронизированы явными барьерами теста | Вход против деактивации/сброса; отзыв против защищённой записи; два bootstrap; параллельное продление/отзыв. Нет действующего устаревшего токена или полномочия |
| Регрессия 0.1 | Проверены подходящие Argon2/CSRF/cookie-примитивы до использования | Не переносить is_admin bypass, create_all, fallback SQLite и ограничитель входа только в памяти. Остаточные данные DOM/logout проверяются позднее вместе с UI |

Гонки тестировать двумя независимыми соединениями PostgreSQL, а не последовательными вызовами. Для отзыва и защищённой записи определить единый порядок блокировок: если отзыв зафиксирован первым, последующая операция отклоняется; уже сериализованная до отзыва операция может завершиться до него. Права и изменение проверяются внутри согласованной транзакции, не по старому кешу. При деактивации/сбросе вход не должен оставить новую действующую сессию. Проверить ограниченные повторы после deadlock/serialization без дублей аудита/полномочий.
