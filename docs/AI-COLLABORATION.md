# Task-Ayuza | Регламент Git и передачи
Справочник к [AGENTS.md](../AGENTS.md). Читать при передаче авторства, конфликте или настройке процесса, не при каждом старте.

## Источники и роли
ТЗ 2.2 и утверждённые D01–D06 определяют продукт; AGENTS.md определяет процесс. [PROJECT_STATUS.md](../PROJECT_STATUS.md) содержит интегрированные факты и одну карточку задачи; [PROJECT.md](../PROJECT.md) сохраняет паспорт, этапы и аудит 0.1.
Исполнитель (Claude Code, Codex или другая доступная среда) выбирается по актуальному поручению владельца и авторству в Issue/PR. Универсального обязательного исполнителя нет; нельзя автоматически назначать frontend/UI/PWA без поручения. ChatGPT может координировать и выполнять read-only ревью; владелец утверждает спорную логику, приёмку и деплой.

## Issue, ветка и PR
- Issue: цель/ID, единственный автор, пути, зависимости, приёмка, тесты, запреты, ветка. GitHub assignee обозначает аккаунт человека, а не идентичность ИИ.
- Один Issue → одна ветка → один PR; исключения обосновываются. Старые ветки не переименовывать. Для явно назначенного Claude допустим прежний формат claude/<issue>-<slug>.
- Во время работы статусы planned/in_progress/blocked/review и доказательства находятся в Issue/PR. blocked не равен accepted. Не копируй туда ТЗ и переписку.
- PR в main: Issue, автор, изменения/контракты, реальные проверки и пропуски, риски, необходимость миграций/деплоя. Используй существующий PR-шаблон. Незавершённый PR остаётся Draft.
- Перед merge сравни с актуальным main и проверь файлы/контракты; конфликты устраняет автор. Предпочтителен squash. Нельзя сливать незавершённую работу ради статуса. После merge удаляй рабочую ветку только при отсутствии зависимых работ.
- Запрет прямого push/force-push в main и обязательное ревью являются правилами процесса. Не заявляй о технической защите GitHub без фактической проверки.

## Единственный писатель и передача
Один набор файлов, миграция, схема или контракт имеют одного автора до завершения PR. Параллельные API/UI допустимы только с утверждённым неизменяемым контрактом, без общих файлов и незавершённых зависимых миграций.
Изменение схемы/API/RBAC/ACL/сценария/D01–D06 требует согласованного влияния до кода; действующее утверждённое задание может содержать это согласование. Иначе только предложение в Issue.
При конфликте: прекратить запись, указать ветки/контракты в Issue, назначить автора разрешения, сверить ТЗ, обновить ветку относительно main, повторить затронутые проверки, передать на ревью. Не перезаписывать чужую работу.
Передача авторства: комментарий Issue/PR с «от/кому», задачей, веткой/SHA, остатком работы и воспроизведением проблемы. Второй исполнитель до передачи только читает. Передавать ссылки, не полные документы.

## Синхронизация
PROJECT_STATUS.md меняется отдельным документационным PR после функционального merge либо тем же PR при исключительном владельце файла. В ветке явно отделяй уже интегрированные факты от предложения. Не редактируй статус в нескольких активных ветках; временные детали оставляй в Issue/PR.
Старые ссылки на текущий статус в PROJECT.md ведут через его начальный указатель к PROJECT_STATUS.md. Исторические задания/отчёты описывают дату составления, а не новое разрешение. PR #1 и #5 объединены; прежняя блокировка M01.1 здесь больше не действует.
Между чатами достаточно AGENTS, краткого статуса, текущего Issue/PR и релевантных разделов. Отдельный PROJECT_CHAT.md не нужен: его функцию выполняет последняя передача в Issue/PR.

## Контроль
Проверяй единственного автора и отсутствие пересечений, правдивость результатов, границы diff, согласованность статуса с main. Требования безопасности и разрешений из AGENTS действуют на любой платформе. Финал формируется по AGENTS; готовый промпт выдаётся при реальной передаче/новом чате или по запросу. Копию промпта в репозитории не накапливать.
