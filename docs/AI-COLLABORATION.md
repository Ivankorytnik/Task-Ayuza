# Task-Ayuza | Совместная разработка Codex и Claude Code

Статус: правила процесса, предложение к включению в main через PR. Не заменяет ТЗ 2.2 и утверждённые D01–D06.

## 1. Источники истины и полномочия
- `docs/TZ-2.2.md` и утверждённые решения D01–D06: бизнес-требования; изменения только после решения владельца.
- `AGENTS.md`: общие правила работы каждого AI-исполнителя; `CLAUDE.md`: короткая точка входа Claude Code, без самостоятельной бизнес-логики.
- GitHub Issue: назначение и границы атомарной задачи; Pull Request: изменения и доказательства проверок; `PROJECT.md` в `main`: последний **интегрированный** статус проекта. Статус незавершённой ветки живёт в её PR, а не выдаётся за статус main.
- Один исполнитель владеет изменением задачи в конкретный момент. По умолчанию Codex реализует backend/БД/API/миграции и тесты, Claude Code — UI/PWA/frontend и связанные тесты. Это разделение по умолчанию, а не разрешение самостоятельно выбирать новый этап. ChatGPT координирует/аудирует; владелец проекта утверждает спорную логику, приёмку и деплой.
- Для работы обоих ИИ над одним модулем назначить одного автора, второго — read-only ревьюером. Передача авторства фиксируется комментарием Issue/PR; второй агент не пушит в чужую ветку без явной передачи.

## 2. Перед началом каждой сессии
1. Читать `AGENTS.md`, `PROJECT.md` из актуального `main`, свою Issue, открытые PR и только релевантные разделы ТЗ. Если работа уже ведётся в ветке, сначала прочитать её PR и исходную точку.
2. Проверить, не заняты ли те же файлы или зависимые контракты другим открытым PR. При пересечении: остановиться, назначить последовательность, не начинать параллельную запись.
3. В Issue указать ID/цель, единственного исполнителя (`Codex` или `Claude Code`), границы файлов, зависимости/блокеры, критерии приёмки, тесты, запреты и ветку. GitHub assignee означает аккаунт владельца/координатора, а не достоверную идентичность ИИ.
4. Для новой задачи создать ветку от свежего `main` после подтверждения, что необходимые предыдущие PR уже слиты. Никаких самостоятельных будущих этапов.

## 3. Git и PR
- `main` — интегрированная версия; прямые коммиты, force-push и удаление истории `main` запрещены правилами команды.
- Формат ветки: `codex/<issue>-<slug>`, `claude/<issue>-<slug>`, `docs/<issue>-<slug>`; существующую ветку `m01-1-postgresql-foundation` не переименовывать.
- Один Issue → одна рабочая ветка → один PR (исключения по документированной необходимости). Коммиты небольшие и тематические. Нельзя складывать несвязанные задачи в один PR.
- PR направлен в `main`; сначала Draft, затем Ready for review после реальных проверок. В описании: Issue, исполнитель, изменённые файлы/контракты, тесты с фактическим результатом, невыполненные проверки, риски, решение о необходимости миграций/деплоя.
- Merge только после ревью, отсутствия конфликтов, прохождения обязательных проверок и явного решения владельца/уполномоченного человека. Предпочтителен squash merge для одного атомарного PR; это организационная рекомендация, не изменение настроек репозитория. Не включать auto-merge.
- Перед merge сравнить PR с актуальным main, проверить список файлов и затрагиваемые контракты, устранить конфликты владельцем ветки. Не применять `--force` для исправления конфликтов.
- Запрещено объединять незавершённый PR лишь для синхронизации статуса. После merge удалить рабочую ветку при отсутствии зависимых работ.

## 4. Синхронизация статусов без конфликтов
- Во время работы исполнитель обновляет **только свой Issue и PR**: `planned → in_progress → blocked → review → accepted/closed`. `blocked` — не `accepted`.
- `PROJECT.md` в main меняется координирующим документационным PR **после слияния** функционального PR либо в том же функциональном PR, если владелец файла назначен исключительно ему. Не изменять `PROJECT.md` одновременно в нескольких активных ветках. При необходимости временно фиксировать промежуточные сведения только в Issue/PR.
- Статус фиксировать фактами: что сделано; какие проверки выполнены/не выполнены; блокеры; открытый PR/commit; следующая атомарная задача с исполнителем. Не писать «готово» без доказательств.
- Перед новой сессией повторно читать `main` + открытые PR, а не доверять прошлому чату. Ссылка на PR/Issue — единственный перенос контекста между Codex и Claude Code.

## 5. Блокировки и интеграционные границы
- Один набор файлов/миграция/контракт API или схема БД — один писатель до завершения PR. Работы над API и UI допустимы параллельно только при утверждённом неизменяемом контракте, без общих файлов и без зависимости от незавершённых миграций.
- Изменение схемы, API, RBAC/ACL, пользовательского сценария или D01–D06 требует явного согласования влияния до кода. Без согласования — Issue с предложением; реализацию остановить.
- Конфликт: (1) прекратить запись; (2) зафиксировать обе ветки и конфликт в Issue; (3) назначить владельца разрешения; (4) сверить с ТЗ; (5) обновить ветку относительно main; (6) повторить тесты; (7) только затем ревью. Не перезаписывать чужие изменения и не принимать решение о бизнес-логике самостоятельно.
- Даже при доступе обоих ИИ к одному GitHub запрещены секреты, реальные ПДн, рабочие БД/дампы и аудио; без отдельного разрешения нет production-операций, деплоя или миграций рабочих баз.
- GitHub Free в приватном репозитории может не предоставлять принудительную защиту `main` через branch protection/rulesets. Поэтому запрет прямого push и обязательное ревью являются **процессными**, пока техническая защита не включена и не проверена. Не заявлять о настроенной защите без проверки.
