## 2. Логическая модель

Общие правила: UUID для сущностей; составные ключи допустимы для таблиц связей. Timestamp хранится как TIMESTAMPTZ, обмен в UTC; календарные сроки как DATE, интерпретация в IANA timezone пространства. Изменяемые сущности имеют created_at, updated_at, version >= 1, archived_at/deleted_at и автора операции, где применимо. Архив и мягкое удаление различаются: архив доступен по фильтру, удалённое видно только в разрешённом режиме восстановления. События не имеют пользовательского CRUD. Физическое удаление связанных объектов по CASCADE не применяется к рабочей истории.

Не хранить универсальное «admin=true ⇒ все данные».

Для полиморфных ссылок в audit/notifications/outbox нет ложного обещания универсального FK: бизнес-сущности используют типизированные FK, служебные ссылки проверяются сервисом. События аудита могут сохранять UUID удалённой сущности; ссылки не должны разрушать аудит. Рабочая DB-роль не получает UPDATE/DELETE на audit/task_events/blocker_events/risk_checks; административное обслуживание под отдельной ролью и регламентом. Это не обещает защиты от владельца самой БД.

Аудио, сырая расшифровка, серверные голосовые черновики отсутствуют в постоянной схеме. Временно принятое аудио удаляется после обработки/ошибки и уборкой осиротевших файлов, исключено из backup. Только вручную подтверждённые название/описание становятся обычным содержимым задачи. Служебная идемпотентность не хранит сырой запрос или транскрипт.

## 3. Ограничения целостности и конкуренция

| Правило | Где обеспечивается |
|---|---|
| Задача относится к своему пространству и проекту | FK workspace_id; составной FK (workspace_id, project_id) на projects; NULL project_id разрешён |
| Команда разрешена в пространстве | FK (workspace_id, executor_team_id) на workspace_teams; активность и право назначения проверяются транзакционно |
| Владелец/исполнитель доступны | FK на users и членство workspace; проверка активности, области доступа и команды; персональный исполнитель обязательно состоит в выбранной команде; исключения в MVP запрещены (D01) |
| Родитель и ребёнок в одном пространстве и проекте, включая оба NULL | FK родителя + отложенная проверка равенства проекта с NULL-safe сравнением; изменение родителя также проверяет детей; обычный составной FK с NULL недостаточен |
| Подзадача без циклов | Проверка пути предков в транзакции; сериализация правок дерева в пространстве. Начальный UI допускает один уровень; модель не требует автоматического создания подзадач |
| Этап, метки | Составные FK внутри пространства/проекта; standalone без этапа |
| Обязательные значения | NOT NULL и CHECK на непустой title, допустимые status/priority, version >= 1; API отличает пропущенное поле от явного NULL и возвращает 422 |
| Даты | start_date <= due_date, когда обе указаны; UTC для событий; закрытие не переписывается обычной правкой |
| Связи без циклов | CHECK A != B, уникальность активной пары; проверка пути от B к A перед A→B. Для MVP единая транзакционная advisory-блокировка графа компании на создание/изменение/восстановление ребра: исключает цикл из двух параллельных запросов |
| Обновление объекта | Атомарное условие id + ожидаемая version, increment version; 409 при устаревании; актуальные права проверяются до раскрытия конфликта |
| Одновременное изменение доступа | Правки членства/грантов и защищённая мутация используют согласованные блокировки/версии ACL в одной транзакции; отзыв не проигрывает старому кешу проверки |
| Изменение + история + outbox | Одна транзакция; ошибка любой записи откатывает весь набор. Повтор после serialization/deadlock ограничен и сохраняет client_key |
| Удаление/архив | FK RESTRICT для рабочих сущностей; мягкое удаление; аудит остаётся. Архив проекта запрещает обычные правки его задач и дочерних объектов |
| Назначение/перенос | Старый и новый контекст проверяются целиком; массовые переносы пространства в MVP не предлагаются. Перенос в другой проект внутри пространства требует прав на оба и согласованности дерева/этапа/ACL |

Архивирование/восстановление не меняет status автоматически. Восстановление связи повторно проверяет цикл; восстановление объекта не оживляет отозванные гранты. Деактивация человека не уничтожает историческое назначение и не назначает замену автоматически; новое назначение неактивному запрещено.

Индексы: tasks(workspace_id, status, id), (workspace_id, due_date, id), (workspace_id, executor_team_id, id), (workspace_id, assignee_user_id, id), (workspace_id, result_owner_user_id, id), (workspace_id, project_id, id), parent_task_id; активные выборки могут использовать partial indexes. Для membership/grants нужны индексы user_id и области; для dependencies оба направления; events(task_id, occurred_at, id), notifications(recipient_user_id, read_at, created_at), sessions(token_hash), sessions(user_id), blockers(blocked_task_id, status). Проверить планы на целевом PostgreSQL, не считать список индексов доказательством скорости.

Все списки имеют стабильную серверную пагинацию (сортировка плюс UUID). Счётчики/аналитика считаются отдельным авторизованным запросом по всей выборке, не по загруженной странице и не с лимитом 2000.

## 4. Матрица объектных прав (утверждено D01–D03)

### 4.1. Единый алгоритм

1. Активная учётная запись, действующая сессия; CSRF для cookie-мутаций; MFA для административных операций.
2. Активное членство нужного пространства либо действующий оформленный administrative_grant. Роль системного администратора не заменяет этот шаг.
3. Проверка конкретного объекта и операции; сервер не доверяет workspace_id/project_id из тела.
4. Проверка назначения команды/человека и второй стороны связи, если применимо.
5. Проверка архива/версии; транзакция; сериализация только разрешённых полей.

Для обычного чтения проектной задачи применяется членство проекта с read **или** самостоятельное основание доступа к этой задаче (назначение/явный grant/уполномоченная команда). Последнее не открывает соседние задачи и закрытые поля проекта. Заголовок/описание проекта не выдаются пользователю с доступом только к задаче: «Проект, подробности недоступны». Автор и владелец результата получают read задачи в своём пространстве; роль observer ограничивает изменения.

Для самостоятельной задачи по умолчанию read: автор, владелец результата, исполнитель, уполномоченные члены команды, администратор с надлежащей областью доступа. Прочие сотрудники даже того же пространства не получают read. Любое расширение записывается в task_access_grants и аудит.

Обозначения: «область» означает только явно разрешённые объекты; «по grant» означает отдельное полномочие, не выводимое из должности. Матрица утверждена вместе с уточнениями § 9.

| История задачи | Read задачи, разрешённые поля | То же | То же | То же | То же |
| Аудит доступа/выгрузок | Отдельный audit_read, без скрытого содержимого | Audit_read в области | Только по audit_read | Нет | Нет |
| Центр рисков | Да по системной роли | Только по роли контролёра рисков | Только по роли контролёра | Только по роли контролёра | Только по отдельному risk_read |

Утверждённые объектные способности участника (D02): автор read/comment/content_edit; владелец результата дополнительно assign/archive_restore/manage_access/link; исполнитель и уполномоченный исполнитель команды read/comment/content_edit/link; член проекта participant получает read/comment/content_edit/create_task/link на задачи проекта. Обычный edit исключает смену workspace, ACL, автора, владельца и назначения. Выдача полномочий допускается только лицом с manage_access и правом делегировать конкретную способность; назначение владельца результата также требует assign. Автор может редактировать/удалять свой комментарий с историей; отдельный moderator может скрыть/восстановить чужой комментарий, но не переписывать текст от имени автора. Все действия требуют доступа к задаче и сохраняют историю.

Совмещение ролей даёт объединение разрешений **в соответствующей области**, observer не отменяет явно выданную другую роль. Глобальные запреты (неактивный пользователь, истёкший grant, архив для обычного edit, потеря членства) имеют приоритет. Снятие одного grant не отменяет другие основания: UI управления доступом должен показывать эффективные права и их причины.

Системный администратор может управлять аккаунтами, но не назначать себе рабочий доступ через косвенное добавление в команду/проект/роль. По D03 такие изменения оформляются тем же процессом одобрения. Первичное назначение лица, уполномоченного одобрять доступ, выполняется владельцем системы по отдельной процедуре, не публичной регистрацией. Нельзя обещать техническую изоляцию от человека с root/DB-superuser: это эксплуатационный контроль вне прикладного RBAC.

### 4.2. Межпространственные связи и отзыв доступа

- Создание, изменение направления, восстановление зависимости требуют link на обе задачи; одно read недостаточно. Удаление связи также требует link на обе стороны; при потере одной стороны вмешивается уполномоченный администратор с доступом к обеим.
- Пользователь с read зависимой задачи получает безопасный индикатор скрытой внешней зависимости без UUID второй задачи, её названия, автора, сроков, людей, комментария связи и статуса. Не отдавать скрытые поля в JSON, totals, подсказках, фильтрах или уведомлениях.
- Поля блокера, способные раскрыть чужую задачу (blocking_task_id, его название и причина связи), требуют прав на обе стороны. Ручное описание блокера является содержимым заблокированной задачи; автору нельзя автоматически подставлять туда текст скрытого объекта.
- Связь риска с задачей не передаёт risk_read пользователю задачи и не открывает задачу контролёру риска.
- После отзыва доступа следующий запрос, экспорт и уведомление проверяют новые права. История не является обходом: old/new скрытых назначений/проектов и межпространственных связей редактируются при сериализации по актуальным полномочиям.
- Предлагаемый HTTP-контракт: 401 без сессии, одинаковый 404 для скрытого/несуществующего объекта, 403 для запрещённого действия на видимом, 409 для видимого конфликта версии, 422 для неверных данных. Ошибка не возвращает скрытые UUID/значения.
- Экспорт выполняется в согласованном снимке данных с проверкой ACL перед выдачей; отозванное во время подготовки право требует отмены/повторной авторизации. Не использовать постоянные публичные ссылки на результаты.
- При смене пользователя/выходе клиент очищает память, карточки и кеши приватных данных; не изображает подтверждённый серверный logout при сетевой ошибке.

## 5. История, закрытия и идемпотентность

Событие статуса записывается только при фактическом переходе. PATCH с прежним status=done меняет прочие поля, но не closed_at и не число закрытий. При выходе из терминального состояния история сохраняется; новое закрытие создаёт новое событие. task_events хранит from/to независимо от будущего выбора аналитических формул.

D04: done и cancelled терминальные для текущего closed_at; исход определяется статусом, события completion и cancellation раздельны. Отмена не считается выполнением. closed_at фиксируется при входе в терминальное состояние и не меняется обычной правкой. Переоткрытие переводит в явно выбранный нетерминальный статус, очищает closed_at и сохраняет событие. Прямые done↔cancelled запрещены: сначала ручное переоткрытие, затем новый исход. Каждый фактический вход в done создаёт completion, в cancelled создаёт cancellation.

Активность существующей зависимости определяется статусом блокирующей задачи: только done снимает вычисляемую активность. Отмена, архив и мягкое удаление сами по себе не снимают зависимость и не меняют статус; архивирование выполненной задачи не делает её невыполненной. Переоткрытие done снова активирует зависимость. Ненужная связь удаляется вручную с причиной и правами link на обе стороны. Статус зависимой задачи автоматически не меняется.

D06: исторические события относятся к назначениям на момент события, текущие показатели к текущему состоянию; текущие права доступа проверяются всегда. Сохраняются история сроков и всех аналитических признаков, включая ответственного за проект, этап, метки и приоритет. Изменения справочников/проекта не должны задним числом менять атрибуцию прошлых событий. Одних текущих FK недостаточно: нужны неизменяемые снимки или версионированная история связанных назначений.

- Выполнения за период: число фактических переходов в done; уникальные выполненные задачи: DISTINCT task_id среди этих событий.
- Переоткрытия: события перехода из done/cancelled в нетерминальный статус. Отмены считаются отдельно и не входят в выполнения.
- Доля выполнения задач со сроком в периоде = 100 × число задач когорты в done на конец периода / число задач когорты. Когорта: доступные сейчас задачи, существовавшие на конец периода, со сроком внутри периода по состоянию на его конец. Срок и статус восстанавливаются из истории на конец периода; события после него не меняют результат. Отменённые включены в знаменатель и показаны отдельно; при знаменателе 0 выводится «Нет данных».
- Пример приёмки: 10 задач со сроком в периоде, на конец периода 7 done, 2 cancelled, 1 открыта: 70%. Это не метрика «выполнено в срок».
- Подзадачи по умолчанию исключены; переключатель одинаково применяется к числителю, знаменателю, событиям, таблицам и графикам. Текущий рабочий список скрывает архив по умолчанию; исторические показатели сохраняют архивные и мягко удалённые объекты в пределах текущих полномочий.
- Границы календарного периода трактуются в timezone пространства; для ещё не законченного периода используется текущий момент с пометкой «неполный период». Исторические срезы на конец периода используют назначения на этот момент, событийные срезы используют назначения при событии.
- Начало достоверной истории фиксируется фактически при вводе надёжной записи событий, а не датой согласования документа. Неполная история 0.1 маркируется legacy/unverified; отсутствие данных не подменяется нулём. Изменение текущего доступа может менять доступную пользователю историческую выборку.

Для создания (ручного или после голоса) один client_key сохраняется клиентом на всю попытку, включая потерю ответа. Создание задачи, idempotency_requests, событие и outbox фиксируются одной транзакцией. Конкурентный повтор с тем же ключом и хешем возвращает тот же resource_id после проверки доступа; другое содержимое с тем же ключом даёт 409. Повтор не создаёт новую задачу/событие/уведомление. Рекомендуемое окно повторов 24 часа с явным запретом автоматического повтора после истечения, значение согласовать до API; UI сохраняет ключ до подтверждённого результата. Повторные мутации с версией также не должны создавать повторных событий.

## 7. Переход на PostgreSQL и Alembic: будущий план

### 7.1. Два разных сценария

**A. Новая установка (базовый путь):** по аудиту в архиве нет БД, в репозитории нет приложения. Создать пустую PostgreSQL по проверенной цепочке Alembic; только технические справочники. Пользователи/пространства/команды и рабочие объекты создаются уполномоченными людьми. Никаких демонстрационных задач, фиктивных событий/релизов и автосоздания проектов.

**B. Обнаружена используемая SQLite:** это условный сценарий, наличие такой БД не установлено. Перенос реальных записей требует отдельного разрешения владельца: ТЗ запрещает импорт рабочих задач без подтверждения, миграция хранения не должна стать обходом. До разрешения только проект процедуры. Рабочую БД/дамп нельзя получать через GitHub или загружать сюда; выполнять перенос на разрешённом российском контуре.

### 7.2. Предлагаемая последовательность ревизий

| Группа | Содержание | Условие готовности |
|---|---|---|
| M01 | users/sessions, organization/workspaces/teams, членства и оформленные полномочия | D01–D03 приняты; права БД/первичный администратор описаны |
| M02 | projects, tasks, назначения, стадии/метки/чек-листы/comments, task_events/audit, idempotency | F01–F03/F13/F14; D04 для closed_at; строгие FK/NULL/версии |
| M03 | зависимости, блокеры, события и связи рисков по готовности risk_register | Графовые ограничения, оба конца ACL, F04–F06; D05 |
| M04 | notifications/outbox, risk_register/risk_checks, releases/export_events | Неизменяемость истории, права, отсутствие ложных релизов/проверок |

Это границы будущих изменений, не готовые migration-файлы и не поручение реализовать весь объём сразу. Каждая ревизия имеет явный parent; один ожидаемый head; последовательность FK учитывает наличие referenced-таблиц. Согласованные изменения схемы выполняются Alembic, приложение не вызывает create_all и не мигрирует при старте. При несовместимой версии схемы startup завершается с безопасной диагностикой.

Фиксировать версии PostgreSQL/SQLAlchemy/драйвера/Alembic после проверки совместимости и лицензий. Не использовать внешнюю платную БД. Роли БД раздельны: migrator с DDL, runtime без DDL/владения схемой, backup по необходимым правам. Прямой доступ браузера к БД запрещён. Секрет подключения только в серверной конфигурации.

Autogenerate выдаёт заготовку, требующую ручного review; отдельно проверять переименования, CHECK, составные FK, partial indexes, отложенные проверки и данные. Нельзя без проверки использовать stamp для объявления существующей схемы соответствующей. SQLAlchemy ORM versioning не заменяет условия version для bulk/manual UPDATE. Межстрочные правила/циклы нельзя выдавать за обычный CHECK.

Для M01–M02 достаточно отдельных небольших этапов. PostgreSQL интеграционные тесты обязательны; SQLite может оставаться только вспомогательным изолированным тестом и не доказывает корректность блокировок/FK/миграций.

### 7.3. Если отдельно разрешён перенос данных 0.1

1. Инвентаризация исходной схемы/версии и контрольных сумм; копия неизменяемого источника на российском носителе; назначить окно остановки записи и восстановление до начала.
2. Таблица ручных соответствий project→workspace, роли→полномочия, task→result_owner/team, status→новый status. Не подставлять владельцем автора/руководителя и не изобретать команду. Противоречивые/пустые значения блокируют перенос затронутых записей и ввод в работу.
3. Проверить UUID, orphan FK, дубликаты логинов после нормализации, циклы parent, даты/часовой пояс naive timestamp, обязательные поля и неизвестные статусы. Не терять/обрезать строки; ошибки в карантин с протоколом на российском контуре.
4. Создать целевую PostgreSQL через проверенные ревизии, переносить в закрытом режиме в порядке FK. Сохранять исходные ID; транзакция/стейджинг и сверка до публикации. Повтор по source-id не создаёт дублей.
5. Не переносить сессии; password hash переносить лишь при подтверждённой совместимости, иначе управляемый сброс без открытых паролей. MFA и административные grant оформляются заново.
6. Исторический completed_at с дефектом 0.1 пометить legacy/unverified. Старый Audit не даёт истории old/new: сохранить свидетельство, но не создавать фиктивные события done/reopen. Историческая аналитика до даты надёжной истории явно неполная.
7. Сверить числа объектов по типам, исходные ID, содержимое, связи, назначения и ACL; все отклонения описать, сверка должна охватывать 100% записей. Нет осиротевших ссылок/неразрешённых ролей.
8. Restore-test независимой копии, приёмка на PostgreSQL, потом отдельное разрешение переключения. До него источник не изменяется, записи в целевую БД пользователям не открываются.

Миграция схемы и миграция данных имеют отдельные протоколы. Сопоставление содержимого может использовать нормализованные хеши, но не заменяет проверку прав/смысла назначений.

### 7.4. Откат

До переключения закрытая целевая БД может быть пересоздана из копии; исходник остаётся неизменным. После появления новых записей в PostgreSQL нельзя просто вернуть SQLite: потеряются новые изменения. Требуются остановка записи, сохранение обеих БД и утверждённый план восстановления/сверки. Разрушительный downgrade не является механизмом восстановления данных. Для production предпочтительны совместимые изменения и исправляющая ревизия; удаление колонок только после отдельного подтверждения и проверенной копии. RPO/RTO и допустимое окно простоя ещё не согласованы.

| F13 | Пользователь видит объекты своего ACL | Чужое пространство; закрытая standalone того же пространства; sysadmin без grant; истёкший grant; observer mutation; самовыдача grant | Единый отказ на detail/list/search/count/analytics/Gantt/export/comments/history/notifications, вложенные поля не утекают |
| F14 | Две сессии читают version=1, первая меняет | Вторая пишет version=1; параллельный отзыв ACL; сбой записи события | Первая версия сохранена, вторая 409 при сохранённом доступе; после отзыва отказ; никаких частичных событий |
| F05 | A→B→C | C→A; одновременно A→B и B→A; восстановление старого ребра | Самоссылки/дубли/циклы запрещены, включая гонку |

| F21 | Разрешённый CSV/JSON | Формула CSV, отзыв доступа при подготовке, чужой фильтр | Экранирование, точный ACL и export_events; нет скрытых строк |

| F25 | 20 сессий, 5000 синтетических задач в тестовом контуре | Параллельные сохранения/ACL/граф; страницы после 2000 | Нет потерь/дублей; все страницы доступны; counts полные; измерения, не обещания скорости |

Дополнительные проверки схемы: ребёнок/родитель оба без проекта; разный проект с одним NULL; перенос родителя с детьми; смена команды; деактивация исполнителя; архив проекта с блокером/комментарием; восстановление не возвращает старые grants. Прямые недопустимые записи в тестовую БД должны отвергаться предусмотренными FK/CHECK/триггерами, а API возвращать безопасную ошибку, не SQL/500.

### 8.3. Будущая приёмка миграций

M-A: чистая PostgreSQL до head, повторное применение без изменений, один head, состояние схемы соответствует metadata и вручную проверенным ограничениям.
M-B: последовательный upgrade каждой поддерживаемой предыдущей ревизии на синтетической копии, контроль данных/индексов/прав; startup не выполняет DDL.
M-C: сбой посередине ревизии/переноса, отсутствие частично опубликованного состояния, повтор без дублей; раздельно проверить нетранзакционные операции, если они появятся.
M-D: runtime не может DDL и переписывать историю; migrator недоступен приложению; нет production-секретов в repo/logs.
M-E: проверенный backup/restore; downgrade лишь там, где обратимость доказана, явная остановка для потери данных.
M-F: условный перенос 0.1 только после отдельного разрешения, с полной сверкой и честным legacy-маркером неполной истории. Если БД 0.1 не существует, сценарий неприменим, а не «пройден».

## 9. Утверждённые решения D01–D06

Основание: явное согласие владельца 11.11.2026 «D01–D06 принимаю по рекомендациям. Исполнитель: Codex».

| ID | Утверждённое решение |
|---|---|
| D01 | Общие команды компании с явной привязкой к пространству. Уполномоченных членов назначает администратор пространства с manage_access и правом делегирования. Членство команды не даёт автоматического доступа. Персональный исполнитель состоит в выбранной команде, исключений в MVP нет; assignee может отсутствовать. |
| D02 | Матрица § 4 принята: участник проекта редактирует задачи проекта, автор редактирует созданную задачу при сохранённом доступе, исполнитель работает с разрешённой задачей. Владелец результата управляет назначениями/архивом/доступом; руководитель управляет проектом без автоматического назначения на задачи. Делегируются только явно разрешённые полномочия; export отдельно. Автор правит свой комментарий с историей; moderator скрывает чужой без переписывания от имени автора. Доступ к задаче не открывает весь проект. |
| D03 | Нет автоматического полного доступа администратора. Первого уполномоченного назначает владелец системы при первоначальной настройке; доступ одобряет владелец или назначенный им уполномоченный, отличный от получателя. Обязательны область, операции, основание и срок: обычный доступ не более 30 дней, продление с новым одобрением; аварийный не более 2 часов, независимое одобрение, MFA и полный аудит. Нужен резервный одобряющий. Самовыдача, включая косвенное членство, запрещена; root/DB-superuser контролируется эксплуатационно. |
| D04 | done/cancelled закрывают задачу с разными событиями; отмена не выполнение. closed_at текущего закрытия неизменен при обычной правке и очищается при переоткрытии. Прямые done↔cancelled запрещены. Только done снимает вычисляемую активность зависимости; отмена/архив/мягкое удаление не заменяют результат, переоткрытие done реактивирует связь. Статусы зависимых задач и блокеров меняются вручную. |
| D05 | У блокера обязателен человек и/или команда. Внешнее назначение не открывает задачу: до отдельной выдачи доступа результат фиксирует уполномоченный участник. Работа с блокером требует edit заблокированной задачи, изменение связи с блокирующей задачей требует link на обе стороны. Снятие ручное, архив/удаление сохраняют историю. |

## 10. Технические основания и фактическая проверка

Официальные документы просмотрены 11.11.2026; они подтверждают технические ограничения, а не готовность Task-Ayuza:
- [Alembic: autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html): миграции требуют ручной проверки, переименование не следует принимать за безопасный add/drop.
- [PostgreSQL: constraints](https://www.postgresql.org/docs/current/ddl-constraints.html): CHECK не гарантирует межстрочные правила; нужны FK/UNIQUE и специально спроектированные транзакционные проверки.
- [SQLAlchemy: version counter](https://docs.sqlalchemy.org/en/20/orm/versioning.html): ORM versioning не защищает произвольный bulk UPDATE/DELETE.

В этой сессии выполнены чтение документов/дерева репозитория, проектная сверка покрытия § 14, семи моделей 0.1 и сценариев F01–F04/F13–F14. После записи проверяются сохранённые тексты и diff. Зависимости, приложение, тесты, БД, миграции и деплой не запускались; численных результатов производительности нет.

Согласование 11.11.2026: выполнена документальная сверка утверждённых D01–D06 с матрицей § 4, жизненным циклом/формулами § 5 и ТЗ. Проверки F01–F37 и дополнительные сценарии выше остаются планом. Код, зависимости, БД, миграции и деплой не затрагивались.
